# AI - 002 — GitHub repo picker misses enterprise org repositories

**Area:** Octocode product — `backend/` GitHub integration + `frontend/` Add-project modal.
**Status:** IMPLEMENTED (iteration 2: org-driven listing + `read:org`). Filed in
`003-EDIT-DELETE/` at the requester's instruction even though it is unrelated to the edit/delete
work.
**Source task:** user report — "it isn't finding my enterprise organizations; I want only what is
from my enterprise, not my personal repos."
**Read together with:** `README.md` §6.6 (endpoints), §6.7 (OAuth flow), §13.3 (GitHub blindspots)
and `tasks/003-EDIT-DELETE/AI - 001.md`.

---

## TL;DR

The project picker is fed by one call: `FetchGithubClient.listRepositories()` issues a **single**
`GET https://api.github.com/user/repos?per_page=100&sort=updated` and maps the result. That is the
whole discovery mechanism.

Consequences:

1. It returns the **first 100** repos accessible to the token, sorted by `updated` — with no
   pagination. Enterprise org repos can simply fall outside the window.
2. It mixes **personal + collaborator + organization** repos. There is no org/enterprise filter in
   the code (no `affiliation`, no `/user/orgs`, no enterprise concept).
3. The OAuth scope is hardcoded `read:user user:email repo` — **no `read:org`** — so the app cannot
   even enumerate your organizations.
4. The GitHub client ignores the `X-GitHub-SSO` header and maps `403`/`404` to generic messages, so
   when an enterprise org blocks third-party OAuth Apps or enforces SAML SSO the result is an empty
   or generic list with no actionable hint.

So "it doesn't find my enterprise orgs" is expected with the current code. GitHub also does not
expose "which orgs belong to my enterprise" for free — that needs `read:org` (REST) or GraphQL,
and enterprise-owned orgs usually additionally require the OAuth App to be approved and/or the token
to be SSO-authorized.

**Implemented (see §4): the repo picker now enumerates the user's organizations (`/user/orgs`, needs
`read:org`) and each org's repos (`/orgs/{org}/repos`), paginated. It falls back to
`/user/repos?affiliation=organization_member` when orgs can't be listed, and surfaces SSO/OAuth-App
blocks with an actionable error. Existing sessions must sign out/in to gain `read:org`.**

## 1. What the code does today (evidence)

| Layer | File | Behavior |
| --- | --- | --- |
| HTTP route | `backend/src/modules/github/routes/github.routes.ts` | `GET /github/repositories` |
| Controller | `backend/src/modules/github/controllers/ListRepositoriesController.ts` | returns the service result verbatim |
| Service | `backend/src/modules/github/services/ListRepositoriesService.ts` | decrypts the user's GitHub token, calls `listRepositories` |
| Client | `backend/src/infrastructure/github/FetchGithubClient.ts` | `GET /user/repos?per_page=100&sort=updated` (single page) |
| Contract | `backend/src/infrastructure/github/GithubClient.ts` | `listRepositories(accessToken)` only; no org/enterprise methods |
| OAuth scope | `backend/src/infrastructure/github/FetchGithubClient.ts` (`getAuthorizeUrl`) | `"read:user user:email repo"` — no `read:org` |
| Frontend | `frontend/src/pages/project/hooks/useGithubRepositories.ts` + `pages/project/components/AddProjectModal.tsx` | fetches once, shows a flat searchable `owner/name` list |
| Docs | `README.md` §13.3 | already records: "GitHub repositories listing uses `/user/repos` … sorted by update" and "Repos and commits fetch only the first page (`per_page=100`); no pagination." |

`GET /user/repos` defaults to `affiliation=owner,collaborator,organization_member` and
`visibility=all`, so organization repos **can** appear. The app adds no `affiliation`, `type`,
`visibility` or `org` parameter, and never follows `Link`/`page` to a second page.

`FetchGithubClient.parse()` handles `401`, `403`, `404`, `409` with fixed messages and does not look
at response headers at all (so the `X-GitHub-SSO` signal is discarded).

## 2. Why enterprise org repos are missing

Ordered by how common each cause is for enterprise orgs. Without access to your account these are
hypotheses; §6 tells you how to confirm which one applies.

| # | Cause | Why it hides repos | Code evidence |
| --- | --- | --- | --- |
| C1 | **Third-party OAuth App access restrictions** — the enterprise/org owner has not approved this OAuth App | GitHub excludes the org's resources from the token; `/user/repos` omits them (or org endpoints return `404`) | No handling; scope is a plain OAuth App, not an installation |
| C2 | **SAML SSO enforcement** on the org, and the token is not SSO-authorized | Repos are hidden until the user clicks "Authorize" for that org; GitHub returns `X-GitHub-SSO` | Header ignored; generic `403`/`404` mapping |
| C3 | **Pagination** — more than 100 accessible repos, sorted by `updated` | Enterprise repos outside the newest 100 never arrive | Single `per_page=100` request, no `page` loop |
| C4 | **No org enumeration / no `read:org`** | Even if we wanted to list per-org, the token cannot read `/user/orgs`; and any "is this an org?" logic is impossible | Scope string lacks `read:org`; contract has no `listOrganizations` |
| C5 | **Enterprise Managed Users (EMU)** | The signed-in identity is enterprise-managed; personal repos live on a different account and the listing semantics differ | Nothing distinguishes EMU; `/user` and `/user/repos` are treated uniformly |
| C6 | **No enterprise filter at all** | The picker intentionally shows everything the token can see (personal + collaborators + orgs) | No `affiliation` parameter, no config, no UI filter |

C1–C3 are the likely reasons it "doesn't find" the orgs. C6 is the reason the list is not "only the
enterprise" even when it works.

## 3. What "only my enterprise, not personal" actually requires

Two separate goals: **(G1) discover the enterprise's repos**, and **(G2) exclude personal ones.**

- **G2 is easy**: `GET /user/repos?affiliation=organization_member` already drops `owner` and
  `collaborator` repos. That alone satisfies "no personal repos" but still spans every org you are
  in, not one specific enterprise.
- **G1 is not free**: REST has no "my enterprise" endpoint usable by a normal member. Options:

| Option | How | Pros | Cons |
| --- | --- | --- | --- |
| **A — affiliation filter** | `GET /user/repos?affiliation=organization_member`, paginated | Smallest change; removes personal repos | All orgs, not a chosen enterprise; still needs pagination + SSO |
| **B — org-driven** | `GET /user/orgs` → `GET /orgs/{org}/repos?type=all`, paginated; UI groups by org | Clean grouping; handles per-org pagination; can let the user pick orgs | Needs `read:org` + re-login; no enterprise grouping |
| **C — enterprise GraphQL** | Add `GITHUB_ENTERPRISE_SLUG`; GraphQL `enterprise(slug:) { organizations { nodes { login } } }` → Option B | True "only my enterprise" | New GraphQL dependency/query; token must access the enterprise; needs a configured slug |
| **D — org allowlist** | Env var listing the enterprise's org logins → Option B filtered to them | Deterministic "only my enterprise", no GraphQL | Manual configuration to maintain |

**Chosen for now (minimal): Option A** — list only organization-owned repos with
`affiliation=organization_member`, paginated. It removes the personal repos and returns every org
you belong to, without `read:org`, GraphQL, an enterprise slug, or a re-login. It does **not**
restrict to a single enterprise and does **not** fix SSO/OAuth-App-restriction blocks (C1/C2) — those
remain possible and are called out in §5 and §7.

Options B–D stay documented above as future work if a single-enterprise filter is needed later.

## 4. Implemented — organization-driven repository listing

**Implemented (two iterations).**

**Iteration 1 (affiliation filter).** `listRepositories` requested
`/user/repos?affiliation=organization_member&type=all`, paginated. It dropped personal repos but,
per the report, enterprise orgs stayed hidden.

**Iteration 2 (org-driven, current).** `FetchGithubClient` now:

1. `listOrganizations` (`/user/orgs`, paginated) — needs the new `read:org` scope.
2. `listOrganizationRepositories` (`/orgs/{org}/repos?type=all`, paginated) for each org.
3. `listRepositories` aggregates them; if `/user/orgs` fails (a token predating `read:org`) or
   returns no orgs, it falls back to `/user/repos?affiliation=organization_member`.
4. If every org is blocked (`403`/`404`), it throws an actionable `403`; the client also reads the
   `X-GitHub-SSO` header and includes the SSO authorization URL in the message.

The `GithubClient` contract gained `listOrganizations`; the OAuth scope changed to
`read:user user:email read:org repo`. The frontend is unchanged (same `GithubRepositorySummary[]`
shape).

Files: `backend/src/infrastructure/github/{GithubClient,FetchGithubClient}.ts`,
`backend/tests/unit/fetch-github-client.test.ts`, `README.md` (§6.7, §13.3, §14.2).

Verification: `npm run typecheck`, `npm run lint`, `npm test` (126 pass) and `npm run build` all
green. Tests stub `globalThis.fetch` (org aggregation + pages, the `/user/repos` fallback, and the
all-orgs-blocked error), so no live GitHub API is used.

**Required from the user:** sign out and back in so the token gains `read:org`; orgs with SAML SSO
must be authorized in GitHub (the error message now links to it), and orgs that restrict third-party
OAuth Apps need an owner to approve the app. The listing still spans **all** the user's orgs, not one
enterprise.

## 6. How to diagnose it right now

Run these with a token from the app account (a classic PAT with `repo read:org`, or the OAuth token):

```bash
TOKEN=<your-token>

# Which scopes does the token actually have?
curl -sS -o /dev/null -D - -H "Authorization: Bearer $TOKEN" \
  https://api.github.com/user | grep -i '^x-oauth-scopes:'

# Can the token see organizations at all? 403/404 here means missing read:org / SSO / org restriction.
curl -sS -o /dev/null -w '%{http_code}\n' -H "Authorization: Bearer $TOKEN" \
  https://api.github.com/user/orgs

# Are org repos returned, and is there an SSO header? (check Link for pagination too)
curl -sS -D - -H "Authorization: Bearer $TOKEN" \
  "https://api.github.com/user/repos?per_page=100&sort=updated" \
  | grep -iE '^link:|^x-github-sso:'

# Only organization repos (the affiliation filter):
curl -sS -o /dev/null -w '%{http_code}\n' -H "Authorization: Bearer $TOKEN" \
  "https://api.github.com/user/repos?affiliation=organization_member&per_page=100"
```

Interpretation:

| Observation | Meaning |
| --- | --- |
| `x-oauth-scopes` lacks `read:org` | The app cannot call `/user/orgs` (C4); the chosen `affiliation` approach does not need `read:org`. |
| `/user/orgs` → `403`/`404` | SSO not authorized or OAuth App restricted (C1/C2). |
| `X-GitHub-SSO: required; ...` on `/user/repos` | Token must be SSO-authorized for that org (C2). |
| `Link: <...&page=2>` present | There are more than 100 repos; the app silently stops at page 1 (C3). |
| `/user/repos` returns only personal repos | The org repos are being filtered out upstream (C1/C2) or are past page 1. |

## 7. Risks and caveats

- **SSO / OAuth-App approval still needs GitHub-side action.** The app now detects `X-GitHub-SSO`
  and reports blocked orgs, but it cannot fetch repos the token is not authorized for. The user must
  authorize SSO (link provided in the error) or have an org owner approve the OAuth App.
- **`read:org` requires a re-login.** Existing sessions keep their old token until they sign out/in;
  until then the code falls back to the affiliation filter and enterprise orgs may stay hidden.
- **All orgs, not one enterprise.** The picker will list every organization you belong to.
- **Personal repos disappear without a toggle.** That matches the request ("only my organizations"),
  but there is no "All repos" option anymore.
- **Rate limits.** Paginating can consume more of the 5,000/hour REST budget than the current single
  call; the page cap bounds it.
- **EMU accounts** are not specially handled (see §5).
