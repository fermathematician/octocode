## TL;DR

The task has four items. Two are structural and two are small:

1. **Sprints become global** (not per-project): remove the project selector, make a sprint span
   all projects. Requires a **schema change** (`Sprint.ownerId` added, `Sprint.projectId` dropped),
   service/DTO changes, and updates to the sprint/kanban/graph/progress frontend.
2. **Sprints get a real date range**: pick start **and** end date instead of the hard-coded
   7-day window (`start + 6d`). Touches sprint validation/service, the create modal, and the
   burndown (which is currently capped to 7 days).
3. **Pushed branches auto-appear as cards** on the sprint/Kanban. New reconciliation service that
   lists GitHub branches and ensures a `Story` card exists for each (skip default branch, skip
   branches with a story). Adds a `Story.imported` flag so auto cards are distinguishable.
   **Caveat:** projects are single-owner today — "all users on a project" is not modelled.
4. **Rewrite `frontend/README.md`**, which still claims the app runs on local in-memory seed data.

Biggest risks: the **data migration** for #1 (backfill `ownerId` from the project owner) and the
**ambiguity/scope** of #3 (what a branch card is, and the missing multi-user model).

## 1. Current state (how it works today)

### Sprints

- `Sprint` **belongs to a project**: `projectId String` (required) → `Project`
  (`backend/prisma/schema.prisma`). There is no `ownerId` on `Sprint`; ownership is derived
  through `project.ownerId`.
- Creation is always 7 days: `CreateSprintService` sets `endDate = startDate + 6`
  (`SPRINT_DURATION_DAYS = 7` in `backend/src/modules/sprints/constants.ts`).
- `POST /sprints` body is `{ projectId, name, startDate }`
  (`backend/src/modules/sprints/validation/sprint.schema.ts`).
- Repository scoping is `where: { project: { ownerId }, ...(projectId ? { projectId } : {}) }`
  (`backend/src/modules/sprints/repositories/SprintRepository.ts`).
- `GET /sprints?projectId=` (paginated).
- A story is auto-attached to the latest sprint **of its project** on create:
  `CreateStoryService` → `sprints.findLatestByProject(projectId)`.
- `MoveStoryToSprintService` refuses a sprint from a different project (400).
- Frontend: `CreateSprintModal` has a **project Select**; `SprintsPage` also filters by project;
  `useSprints` builds overviews keyed by `sprint.projectId`.

### Burndown / active sprint

- `frontend/src/domain/sprint.ts`:
  - `latestSprintPerProject(sprints)` and `selectActiveSprints(sprints, projectId)` choose the
    latest sprint per project.
  - `buildBurndown` caps the window at `SPRINT_DURATION_DAYS - 1` (6), i.e. 7 days.
- `useKanban`, `useBurndown`, `useProjectProgress` all fetch projects + sprints + stories and
  compute overviews on the client.

### Branches / cards

- A **card is a `Story`**. Stories are created manually (`CreateStoryForm`) with a required
  `branch` chosen from the branch picker.
- Branch sources: `GET /github/projects/:projectId/branches` merges **GitHub** branches and
  **local** branches reported by the git hook (`LocalBranch` model,
  `scripts/git-hooks/octocode-branch-sync.mjs`).
- `Story` is unique per `(projectId, branch)`.
- Commit sync (`SyncCommitsService`, `SyncStoryCommitsService`) selects the story branch (or the
  default branch when merged) and upserts commits. It **never creates stories**.
- The SPA syncs commits on Kanban/Backlog open via `POST /github/sync`.

### Project ownership

- `Project.ownerId → User` (**single owner**). There is **no membership / roles / collaborators**
  model (root `README.md` §9 item 9, §14 Phase 5). "All users on a project" is therefore not a
  real concept in the product yet.

(The word "branch" is used loosely for the planning box; the fixed 7-day window is a sprint property.) |

### Assumptions (stated, not asked)

- **A1.** "sprint" in #1/#2 is the planning time box, not a git branch. Evidence: the only model
  with a 7-day rule is `Sprint`; git branches have no dates.
- **A2.** A "card" in #3 is a `Story` (the only movable board entity). Cards are created
  automatically from branches that lack a story.
- **A3.** Multi-user projects are **out of scope** for this round. Within the current single-owner
  model, the owner's GitHub token can list all branches in the linked repository, so teammates'
  pushed branches do become cards for the owner. True cross-user visibility waits for project
  membership (documented as a dependency, not built here).
- **A4.** Sprints stay per-user (`ownerId`), never shared across accounts.
- **A5.** No new dependencies.

If A2 or A3 is wrong, fix #3 changes shape; see §8.

## 3. Design decisions

| #   | Decision                                                                                                                                                        | Rationale                                                                              |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| D1  | `Sprint` gains `ownerId → User` and **loses** `projectId`.                                                                                                      | Sprints must be listable/scoped per user without routing through a project.            |
| D2  | A sprint has **no** project relation. Per-project views derive the project from the sprint's **stories**.                                                       | A global sprint can contain stories from several projects.                             |
| D3  | `POST /sprints` body becomes `{ name, startDate, endDate }`. `PATCH` accepts `endDate`.                                                                         | Removes the project selector; supports custom ranges.                                  |
| D4  | `endDate >= startDate` is enforced in the service (`AppError` 400) and in the create form.                                                                      | Cross-field rule; both ends are user input.                                            |
| D5  | `UpdateSprintService` **never** recomputes `endDate`; it only applies explicit fields.                                                                          | Duration is now user-controlled.                                                       |
| D6  | Burndown uses the sprint's real `startDate`→`endDate` range; the 7-day cap is removed.                                                                          | Must match custom durations.                                                           |
| D7  | `Story` gains `imported Boolean @default(false)` (auto-created branch cards only).                                                                              | Lets reconciliation manage only its own rows and lets the UI tag them.                 |
| D8  | Auto-imported cards: title = humanized branch, `storyPoints = 1`, `priority = medium`.                                                                          | Safe defaults; humans refine them.                                                     |
| D9  | Auto-imported card placement: if the user has a current/latest sprint, attach the card to it with `status = code`; otherwise create it as `backlog`/unassigned. | The user asked for a card "on the sprint / kanban"; `code` reflects a pushed branch.   |
| D10 | Reconciliation **skips** the repository default branch and any branch that already has a story.                                                                 | Default branch is not a feature; `(projectId, branch)` uniqueness prevents duplicates. |
| D11 | Branch reconciliation is a separate service from commit sync, orchestrated by one call site.                                                                    | Keeps single-responsibility (skills: one service per use case).                        |
| D12 | Reconciliation runs for the **repository owner** (`GithubRepository.userId`).                                                                                   | That is whose token can read the repo.                                                 |

Decisions D8/D9 are preferences and can be flipped cheaply; flag them in review.

### 4.3 Fix 3 — auto branch cards

Builds on Fix 1.

**Schema**: `Story.imported Boolean @default(false)` (migration `..._story_imported`).

**Backend — new service** `modules/github/services/SyncBranchStoriesService.ts`
(mirrors `SyncCommitsService`):

```
executeForUser(ownerId) | executeAll() | executeForRepository(repository)
  for each repository:
    token = decrypt(owner's GITHUB OAuthAccount)
    branches = githubClient.listBranches(token, repo.owner, repo.name)   // paginated by client
    known   = storyRepository.findBranchesByProject(repo.projectId)
    active  = sprintRepository.findLatestByOwner(repo.userId)            // D9
    for each branch not in known and != repo.defaultBranch:
      storyRepository.create({
        projectId, sprintId: active?.id ?? null,
        title: humanizeBranch(branch), storyPoints: 1, priority: MEDIUM,
        status: active ? CODE : BACKLOG, branch, imported: true,
      })
  return { created: n }
```

- `humanizeBranch`: strip a leading `feat/` `fix/` `chore/` `hotfix/` `bugfix/` prefix, replace
  `[-_/]` with spaces, capitalise the first letter; fall back to the raw branch.
- Add a helper in `backend/src/shared/branch.ts` (e.g. `titleFromBranch`) + unit tests.
- `StoryRepository` gains the fields on `CreateStoryData` (`imported`) and a mass-insert isn't
  needed (volume is low); keep one create per branch, catching `P2002` (already 409-mapped) to stay
  idempotent under races.

**Backend — orchestration / endpoint**

- New application orchestrator `SyncRepositoriesService` that runs `SyncBranchStoriesService`
  then `SyncCommitsService` for a user/repo, returning
  `{ branchesCreated, stories, commits }`.
- Point `POST /github/sync` (the SPA "sync on open") at the orchestrator. Background
  (`server.ts`) and webhook (`HandleGithubWebhookService`) call the same orchestrator so pushed
  branches and commits both propagate.
- `SyncCommitsService` stays commit-only; `SyncStoryCommitsService` unchanged.

**Frontend**

- `api/github.ts`: extend `SyncAllCommitsResult` with `branchesCreated` (rename if desired).
- No new UI required: cards appear because Kanban/Backlog/Sprints already read stories and run
  sync-on-open. Optional: tag `imported` cards in `KanbanCard`/`StoryCard` with a small badge.
- `domain/types.ts`: add `imported: boolean` to `Story`; `shared/presenters.ts`: map it.

**Multi-user caveat (A3)** — this fix does **not** let different accounts share a project. It makes
all branches of the linked repository visible to the project owner. A real "all users on a project"
needs membership (new model, joins, authorization) and is recommended as a separate task.

## 5. Migration sketch

Two migrations, applied with `npm run prisma:migrate`. Because #1 needs a backfill, the migration
SQL is authored by hand (Prisma generates the shape; we add the `UPDATE`).

**`..._global_sprints`**

```sql
-- 1. add the new owner column (nullable at first)
ALTER TABLE "Sprint" ADD COLUMN "ownerId" TEXT;

-- 2. backfill from the owning project
UPDATE "Sprint" s
SET "ownerId" = p."ownerId"
FROM "Project" p
WHERE s."projectId" = p."id";

-- 3. enforce it
ALTER TABLE "Sprint" ALTER COLUMN "ownerId" SET NOT NULL;

-- 4. remove the project link
ALTER TABLE "Sprint" DROP CONSTRAINT "Sprint_projectId_fkey";
DROP INDEX "Sprint_projectId_idx";
ALTER TABLE "Sprint" DROP COLUMN "projectId";

-- 5. scope by owner
CREATE INDEX "Sprint_ownerId_idx" ON "Sprint"("ownerId");
ALTER TABLE "Sprint"
  ADD CONSTRAINT "Sprint_ownerId_fkey"
  FOREIGN KEY ("ownerId") REFERENCES "User"("id")
  ON DELETE CASCADE ON UPDATE CASCADE;
```

**`..._story_imported`**

```sql
ALTER TABLE "Story" ADD COLUMN "imported" BOOLEAN NOT NULL DEFAULT false;
```

Constraint/index names are illustrative — mirror whatever the generated migration uses.

## 8. Risks and open questions

1. **Migration risk (#1).** Dropping `projectId` is destructive. The backfill preserves ownership;
   per-project sprint associations are intentionally dropped (derivable from stories). Verify on a
   seeded DB before shipping. `Yes, you have permission to do it`
2. **"All users on a project" is not modelled (A3).** Without membership, fix #3 only serves the
   owner. Decide: accept the owner-scoped behaviour now, or schedule project membership as a
   prerequisite. This is the single biggest scope question. `es, owner scoped. teh idea is to integrate all backlong on just one kanban`
3. **Auto cards pollute the backlog/board (#3).** Every stale/experimental branch becomes a card
   with points 1. Mitigations to consider: only import branches updated recently, an env flag
   (`GITHUB_IMPORT_BRANCHES`), or a dedicated "branches" lane. Defaults D8/D9 are guesses. `Only the ones made after the sprint run should appear automatically`
4. **Orphan cards (#3).** When a branch is deleted upstream, the imported card remains (commits are
   never pruned either). Decide whether reconciliation deletes `imported` stories for vanished
   branches (destructive) or leaves them. `Yes, leave them. no destructive behaviour`
5. **Rate limits (#3).** Listing branches for every repo on every sync adds GitHub calls; the
   background interval (`GITHUB_COMMIT_SYNC_INTERVAL_MS`) already runs frequently. Consider reuse
   of the branch list already fetched for the picker, or a longer interval. `we will use the list of fetched`
6. **Same-day / long sprints.** `buildBurndown` guards `totalDays` with `Math.max(1, …)`; confirm
   the ideal line stays sane for 1-day and multi-week sprints. `Confirmed`
7. **`SPRINT_DURATION_DAYS` removal.** Used only by the two sprint services today — confirm no
   other import before deleting. `Confirm. go ahead and delete`
8. **Frontend pagination.** Still first-page only (root README §9); auto cards increase volumes but
   the default limit is 100. Note, do not fix here. `Yes, do not change`
